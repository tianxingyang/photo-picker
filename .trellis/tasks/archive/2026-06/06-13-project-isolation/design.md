# Design — Project-based workspace isolation

Source of truth for requirements: `prd.md`. This file is the technical design.

## 1. Architecture & boundaries

A **project** is the unit of isolation. The app keeps a single SQLite DB and a
single `Connection`, but every photo row, group row, and group-member row is
owned by exactly one project. Exactly one project is "open" at a time; the open
project id lives in process state, not in each command's arguments.

```
Landing (project list)  ──open_project(id)──▶  Grid (existing browse view)
        ▲                                             │
        └──────────── close_project() ────────────────┘
```

### Scope-threading mechanism (decided: option A)

`AppState` gains `current_project: std::sync::Mutex<Option<String>>` (`None` =
no project open). The value is a project **UUID** string.

- `open_project(id)` validates the project exists, stores `Some(id)`, and
  updates `projects.last_opened_at`.
- `close_project()` resets to `None` (used when the user returns to the landing
  page to switch projects).
- Every photo-scoped command reads + clones the current id at entry (a brief
  synchronous lock, never held across `.await` or into `spawn_blocking`). If
  `None`, it returns `AppError::Validation("no project open")` — a guard that
  makes "a command ran without an open project" a loud failure, not silent
  global access.
- The single-flight guards (`analysis_running`, `grouping_running`) stay global
  and unscoped: only one project is open at a time, so they cannot leak across
  the project boundary (AC9 holds by construction, not by per-project flags).

`std::sync::Mutex<Option<String>>` (not the tokio Mutex used for `db`/`sidecar`)
because the read is a trivial clone done synchronously before any await — no
need for an async lock. A `String` (not `i64`) because the project id is a UUID
(see below).

### Project id = UUID (decided 2026-06-14, Q5)

`projects.id` is a **UUID v4 string** (e.g. `"3f2c…"`), generated backend-side
in `create_project` via the `uuid` crate. Chosen over an INTEGER surrogate so
the id is non-sequential, non-guessable, and stable/portable across any future
DB rebuild or project export-import — it never depends on insertion order or
autoincrement state. Cost: 36-char text PK + FK instead of an 8-byte int
(negligible at this scale).

### Photo id derivation (R1, R3)

Today: `id = blake3(path)` (scanner/mod.rs:66). New:

```
id = blake3(format!("{project_id}\n{path}"))   // project_id = uuid; hex, 64 chars
```

The `\n` separator keeps the two fields unambiguous. The same path in two
projects yields two different ids → two independent rows (R3, AC2, AC4). Ids
stay globally unique across projects, so `set_status` / `transcode_for_display`
remain correct keyed by `photo_id` alone (no project filter needed — a project-A
id never collides with a project-B id).

## 2. Data model & migration

### New `projects` table

```sql
CREATE TABLE projects (
  id             TEXT PRIMARY KEY,         -- UUID v4, generated in create_project
  name           TEXT NOT NULL,
  created_at     TEXT NOT NULL,            -- RFC3339 UTC
  last_opened_at TEXT                      -- NULL until first open
);
```

`id` is a UUID v4 string (rationale in §1) — generated by the backend, never
exposed as a sequential number.

### `photos` / `similar_groups` / `group_members` rebuild

`photos` must gain `project_id`, drop the global `path UNIQUE`, and change its
PK derivation; `similar_groups` must gain `project_id` so grouping can
delete/rebuild only the open project's groups. SQLite cannot ALTER a PK or drop
a column UNIQUE in place, and **R5 discards all existing data**, so migration
`0004` drops and recreates all three tables:

```sql
-- 0004_projects.sql
CREATE TABLE projects ( ... );             -- as above

DROP TABLE group_members;
DROP TABLE similar_groups;
DROP TABLE photos;

CREATE TABLE photos (
  id             TEXT PRIMARY KEY,         -- blake3(project_id \n path)
  project_id     TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  path           TEXT NOT NULL,
  status         TEXT NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','keep','reject')),
  created_at     TEXT NOT NULL,
  shot_at        TEXT,
  blur_score     REAL,
  is_blurry      INTEGER CHECK (is_blurry IN (0,1)),
  exposure_score REAL,
  exposure_flag  TEXT CHECK (exposure_flag IN ('normal','over','under')),
  phash          TEXT,
  analysis_state TEXT NOT NULL DEFAULT 'pending'
                 CHECK (analysis_state IN ('pending','done','failed')),
  analysis_error TEXT,
  UNIQUE (project_id, path)                -- path unique WITHIN a project
);
CREATE INDEX idx_photos_project        ON photos(project_id);
CREATE INDEX idx_photos_status         ON photos(status);
CREATE INDEX idx_photos_analysis_state ON photos(analysis_state);
CREATE INDEX idx_photos_shot_at        ON photos(shot_at);

CREATE TABLE similar_groups (
  id         TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  method     TEXT NOT NULL,
  params     TEXT NOT NULL
);
CREATE TABLE group_members (
  group_id TEXT NOT NULL REFERENCES similar_groups(id) ON DELETE CASCADE,
  photo_id TEXT NOT NULL REFERENCES photos(id)         ON DELETE CASCADE,
  PRIMARY KEY (group_id, photo_id)
);
CREATE INDEX idx_group_members_photo    ON group_members(photo_id);
CREATE INDEX idx_similar_groups_method  ON similar_groups(method);
CREATE INDEX idx_similar_groups_project ON similar_groups(project_id);
```

Migration runner (db/mod.rs:27) is forward-only by `user_version`; appending
`0004` to the `MIGRATIONS` array bumps the dev DB to v4 on next launch. The
existing dev DB rebuilds to empty tables (AC8). `DROP TABLE` requires the FK
pragma not to block — drops cascade fine; order is members → groups → photos to
respect references even though we drop+recreate.

> Delete-project cascade (AC7) is free: `ON DELETE CASCADE` on
> `photos.project_id` and `similar_groups.project_id` means `DELETE FROM
> projects WHERE id=?` clears that project's photos and groups; group_members
> cascade off both photos and groups. Requires `PRAGMA foreign_keys=ON` — db.rs
> already sets it (db/mod.rs:23).

## 3. Command layer (contracts)

### New commands (commands/projects.rs)

| Command | Args | Returns | Notes |
|---|---|---|---|
| `create_project` | `name: String` | `ProjectSummary` | generate UUID v4; insert row; `created_at=now`; does NOT auto-open |
| `list_projects` | — | `Vec<ProjectSummary>` | left-join photo count; order by `last_opened_at` desc nulls last, then `created_at` desc |
| `open_project` | `project_id: String` | `()` | validate exists → set current → update `last_opened_at=now` |
| `close_project` | — | `()` | set current to `None` |
| `delete_project` | `project_id: String` | `()` | `DELETE FROM projects WHERE id=?` (cascade); if it equals current, also reset current to `None` |

```rust
#[derive(Serialize)] #[serde(rename_all = "camelCase")]
struct ProjectSummary {
  id: String,            // UUID v4
  name: String,
  created_at: String,
  last_opened_at: Option<String>,
  photo_count: i64,
}
```

`create_project` generates the id with the `uuid` crate
(`uuid::Uuid::new_v4().to_string()`) — add `uuid = { version = "1", features =
["v4"] }` to `src-tauri/Cargo.toml`.

### Existing commands — scoping changes

| Command | Change |
|---|---|
| `scan_folder` | read `project_id` from state (err if none); pass into `scanner::scan_folder`; id = `blake3(project_id \n path)`; INSERT includes `project_id`; SELECT-back filters by id (already unique) |
| `set_status` | **no change** — `photo_id` is globally unique & project-encoded |
| `transcode_for_display` | **no change** — keyed by `photo_id` |
| `export_keep` | `select_keep_paths` gains `WHERE status='keep' AND project_id=?` with project from state |
| `analyze_pending` | pending SELECT gains `AND project_id=?`; persist is by id (unchanged) |
| `group_photos` (`regroup`) | photo SELECT gains `WHERE project_id=?`; DELETE groups gains `AND project_id=?`; INSERT `similar_groups` includes `project_id` |
| `list_groups` (`load_browse_model`) | grouped JOIN and ungrouped SELECT gain `WHERE/AND p.project_id=?`; `similar_groups` insert/read scoped |

A small helper centralizes the read + guard:

```rust
fn current_project(state: &AppState) -> Result<String, AppError> {
    state
        .current_project
        .lock()
        .unwrap()
        .clone()
        .ok_or_else(|| AppError::Validation("no project open".into()))
}
```

The id is cloned out before `spawn_blocking` and moved into the closure (same
pattern as the `db` Arc clone), so the lock is never held across `.await`.

### lib.rs registration

Register the five new commands in `invoke_handler![...]` (lib.rs:63). Add
`current_project: std::sync::Mutex::new(None)` to the `AppState` construction
(lib.rs:41).

## 4. Frontend

### API layer (src/api/projectsApi.ts — new)

`createProject(name)`, `listProjects()`, `openProject(id)`, `closeProject()`,
`deleteProject(id)`. Each validates the boundary shape like `photosApi`
(`isProjectSummary`). Tauri camel↔snake: `projectId` ↔ `project_id`.

### State (src/store/projectsStore.ts — new)

```ts
type ProjectsState = {
  projects: ProjectSummary[];
  currentProjectId: string | null;   // UUID; null => show Landing
  loadProjects(): Promise<void>;
  open(id): Promise<void>;            // openProject + set current + hydrate grid
  close(): Promise<void>;            // closeProject + clear photo/group/compare stores + display cache
  create(name): Promise<ProjectSummary>;
  remove(id): Promise<void>;
};
```

### Routing (src/App.tsx)

App becomes a two-state router on `currentProjectId`:

- `null` → `<LandingView />` (project list + create + delete).
- set → the existing header + `<GroupBrowseView />`, plus a **「切换项目」**
  header button calling `projectsStore.close()`.

Opening a project must **clear** `photosStore`, `groupsStore`, `compareStore`
and call `clearDisplayCache()` before hydrating, so project B never shows project
A's cached transcodes or grid state. Closing does the same.

### LandingView (new component) — via `ui-ux-pro-max`

Project list rows show **name + photo count + last-opened**; a create control
(name input) and a per-row delete with a confirm dialog (AC5–AC7). All visible
UI is designed/built through the `ui-ux-pro-max` skill per project convention.

## 5. Tradeoffs & risks

- **Test-fixture churn (highest-effort risk).** The unit-test `mem_conn()`
  helpers in `scanner`, `analysis`, `grouping`, and `photos` test modules apply
  migrations `0001..0003` and INSERT photos with no `project_id`. After `0004`
  they must apply `0004` and seed a `projects` row + `project_id` on every photo
  insert. This is mechanical but touches ~4 test modules and many fixtures.
- **Discarding data is intentional (R5).** No id-recompute / carry path is
  written. If a real user had real labels this would be lossy — accepted because
  the current DB holds only dev test imports.
- **`set_status` left unscoped by design.** Relies on the id being
  project-encoded and globally unique. A defensive `AND project_id=?` is
  possible but adds a state read to a hot single-row path for no isolation gain;
  omitted deliberately and noted here so it isn't "fixed" later by mistake.
- **Single global connection retained.** Per-project DB files were rejected in
  R1; this design keeps one connection and one WAL, scoping by column.

## 6. Rollout / rollback

- Rollout: ship migration `0004` + backend scoping + frontend landing together;
  there is no partial-isolation intermediate state worth shipping.
- Rollback: revert the branch. Because `0004` dropped+recreated tables, a
  rollback to pre-0004 code on an already-migrated DB would see `user_version=4`
  and skip migrations, but the v4 schema has extra columns the old code doesn't
  query — old code would fail on `project_id NOT NULL` inserts. Rollback
  therefore requires deleting the dev DB file (acceptable per R5). Documented so
  a rollback isn't attempted in place.
